# Среда, изоляция и автономный запуск: проект реализации

Статус: архитектурный reference. G0/G1/G2 реализованы; Linux sandbox проверен наARM64 совместно с полной валютной моделью. [Текущий отчёт](../STAGE2_STATUS.md) содержит529 tests/23 acceptance checks; раздел14 ниже сохраняет историю раннегоG0. Готовность всей сдачи и официальные баллы не заявляются.

Автор направления: `environment_design`. Интеграционные решения согласуются с `data_design`, `evaluation_design` и главным планом. При расхождении нормативным становится итоговый общий план. [Исторический отчёт G0/G1](../STAGE1_STATUS.md) сохранён отдельно.

## 1. Что требует кейс, а что выбираем мы

**Требования кейса:** JSON-совместимый контракт `reset(seed, config)` / `step(action)`; максимум 100 действий с учётом отправки; перечисленные пять инструментов; страницы максимум 50 строк; воспроизводимость; только запрошенные открытые записи; закрытый эталон и seed недоступны агенту; оценщик вне процесса агента; нулевая награда за исследование; в закрытом прогоне награда и диагностика остаются у оценщика до конца прогона; траектории; автономная проверка без сети, платных API и GPU. Python 3.11 / 2 CPU / 4 GB / 1 GB / 60 секунд на эпизод указаны как предлагаемые ограничения.

**Наши проектные решения:** Python 3.11; потоковый JSONL-протокол через pipes; отдельный доверенный supervisor и изолированный процесс агента; Linux Docker как поддерживаемая среда безопасной проверки; отдельный локальный cooperative-режим для разработки; строгая схема действий; нейтральная wire-награда `0` во всём закрытом прогоне; явная машина состояний; ранний security spike с запретом тихого снижения защиты.

**Неполнота источника:** полный набор фиксированных проверок организаторов в предоставленном PDF отсутствует. Раздел 12 перечисляет трактовки, которые нужно подтвердить; собственные тесты не будем называть официальными.

## 2. Границы модулей и доверия

```text
Trusted supervisor
  ├── generator + independent data validator
  ├── public record store (read-only API)
  ├── private truth / provenance / evaluator
  ├── budget + clock + terminal state
  ├── private evaluation log and trajectory writer
  └── JSONL broker ── stdin/stdout ── isolated agent worker
                                      └── public observation + action client only
```

Агент не получает объект Python-среды, замыкания, сериализованный конфиг генератора, путь к эпизоду или дескриптор оценщика. Его интерфейс состоит из JSON-значений. Сериализация pickle запрещена.

Генератор и оценщик могут жить в одном доверенном процессе: требование состоит в отделении оценщика от агента. Объект агента никогда не импортируется и не исполняется в trusted process; исключение — явно обозначенный cooperative-режим, который не используется как доказательство изоляции.

Объекты публичных наблюдений создаются заново на каждом шаге; возвращённые раньше словари не изменяются при дальнейших действиях. Record store не выдаёт изменяемые ссылки на внутреннее состояние.

### Trusted reset и agent-facing start

`AuditEnv.reset(seed, config)` вызывается только доверенным harness. Именно эта фасадная функция удовлетворяет контракту кейса. Она генерирует/загружает эпизод, очищает состояние и возвращает `(observation, info)`.

Агент получает отдельное сообщение `start`, содержащее только результат reset: задачу, публичный manifest, краткую публичную политику и 100 оставшихся шагов. Ни seed, ни private-часть config не пересылаются. Агент не выбирает новый seed, не сбрасывает эпизод и не получает Python-атрибуты фасада. Попытка вызвать инструмент `reset` считается неизвестным действием.

Изображение/контейнер и публичный `episode_id` не должны иметь seed в имени или метаданных. `episode_id` не равен seed и не является его прямым строковым представлением или хешем. Идентификаторы создаются отдельным presentation RNG. Это защита от прямого раскрытия; восстановление seed из полностью известного детерминированного генератора при маленьком пространстве seed не является криптографически решённой задачей. Для наших закрытых прогонов используем большие seed; правила официальных seed нужно уточнить.

## 3. Публичный протокол и инструменты

Предлагаемая единая форма действия:

```json
{"action":"list_records","args":{"table":"ledger","cursor":null,"limit":50}}
```

Это проектная форма wire, а не утверждение о пока не опубликованной форме адаптеров организаторов. Python facade преобразует её в `step(action)`.

Общие правила: UTF-8; один JSON-объект на frame; строгие типы; запрет `NaN`/`Infinity`; запрет повторяющихся ключей; ограничение размера и вложенности; неизвестные ключи не игнорируются молча. `bool` не принимается вместо целого числа. Ограничения wire опубликованы в схеме.

| Действие | Аргументы | Результат | Существенные ограничения |
|---|---|---|---|
| `list_records` | `table`, `cursor`, `limit` | Полные открытые записи с публичными ID, `next_cursor` | Таблица из allowlist, `1 <= limit <= 50`, стабильная пагинация |
| `get_record` | `table`, `id` | Одна полная открытая запись | ID должен принадлежать указанной таблице текущего эпизода |
| `get_document` | `doc_id` | Один открытый документ | Только реестр документов текущего эпизода; никакой интерпретации ID как пути |
| `calculator` | `expression` | Десятичная строка результата | Только ограниченная арифметика, без кода/файлов/вызовов функций |
| `submit` | `findings` | Терминальное подтверждение | `findings` — объект `{episode_id, findings:[...]}` по схеме кейса |

Конкретный submit wire:

```json
{"action":"submit","args":{"findings":{"episode_id":"public-opaque-id","findings":[]}}}
```

Обязательные CSV/JSON поля не меняем ради адресации. `fx.csv` получает стабильные публичные record ID в tool-envelope/индексе, а не скрытые anomaly labels. `get_document("policy")` возвращает полную `policy.json`; summary этой политики находится также в reset. ID `policy` является зарезервированным публичным адресом, а не файловым путём.

Пример результата инструмента:

```json
{
  "observation": {
    "result": {"records": [], "next_cursor": null},
    "remaining_steps": 99
  },
  "reward": 0,
  "terminated": false,
  "truncated": false,
  "info": {}
}
```

Trusted Python `step` возвращает ту же семантику как `(observation, reward, terminated, truncated, info)`.

Ошибки используют короткие стабильные коды (`invalid_action`, `invalid_arguments`, `record_not_found`, `invalid_cursor`, `calculation_error`). Никаких traceback, абсолютных путей, SQL, repr внутренних объектов или данных эталона. Не включаем в ошибку неограниченный пользовательский ввод.

### Пагинация и достижимость доказательств

Табличный порядок фиксируется при reset и не меняется в пределах эпизода. Курсор — непрозрачный токен без seed, количества ошибок или private labels. Он связан с эпизодом, таблицей и позицией; не подменяется индексом закрытого файла. Невалидный, чужой или устаревший токен даёт ограниченную ошибку. Одинаковая последовательность запросов в воспроизведённом эпизоде создаёт одинаковые курсоры.

`list_records` возвращает содержимое записей, а не только ID: при 200 документах отдельный запрос каждого документа был бы несовместим с бюджетом 100 шагов. Согласованная с data-направлением граница supported config:

- до 2000 строк ledger: максимум 40 страниц;
- суммарно до 200 invoice/payment-документов: максимум 5 страниц при разделении на две таблицы;
- до 200 FX-записей: максимум 4 страницы;
- полная policy: 1 запрос.

Итого полное чтение укладывается в 50 inspection-действий. Остаётся бюджет на калькулятор и submit. Это конструктивная верхняя граница доступа к информации, не доказательство того, что агент умеет найти правильное решение. Независимая проверка содержания доказательств остаётся обязательной. Config, превышающий этот supported bound, отклоняется доверенным preflight до запуска агента; возможность расширения масштаба документируем отдельно.

## 4. Машина состояний и точные границы

Состояния: `UNINITIALIZED -> ACTIVE -> TERMINATED | TRUNCATED`. Новый trusted reset создаёт новый ACTIVE-эпизод и полностью очищает записи, курсоры, бюджет, результаты и таймер.

Два счётчика, которыми владеет только supervisor:

- `total_steps`: все обработанные попытки действий активного эпизода, включая submit и ошибки;
- `inspection_steps`: все такие попытки, кроме распознанного submit. Включает неверный ID, неизвестное действие, ошибки аргументов и калькулятора.

Submit входит в 100, но не в штраф за inspection. Это согласованная проектная трактовка; её нужно подтвердить у организаторов.

Порядок обработки:

1. Если эпизод уже завершён — вернуть ограниченную protocol error без новой оценки, шага и перехода. Trusted facade может использовать `EpisodeFinished`; публичный broker не возвращает повторно терминальную награду.
2. Если deadline уже достигнут — truncate с пустым итоговым ответом. Не выполнять действие.
3. Принять ограниченный frame; увеличить `total_steps`. Для не-submit увеличить `inspection_steps`.
4. Если это submit: проверить структуру. Корректный submit оценивается один раз и завершает эпизод с `terminated=true`. Структурно неверный submit также терминален, trusted reward `-1`, диагностика только в evaluator log.
5. Иначе выполнить инструмент/сформировать bounded error. Если после действия `total_steps == 100`, завершить с `truncated=true` и пустым итоговым ответом. Иначе остаться ACTIVE.
6. Жёсткий wall timeout прерывает зависший агент/tool; итоговый ответ пустой. Тайм-аут не даёт использовать частично подготовленные findings.

Таким образом, submit на 100-м шаге допустим; 100-е исследовательское/неверное действие исчерпывает лимит. Step 101 не существует. Неудачные запросы не позволяют бесконечно исследовать записи бесплатно.

Валидное действие должно завершиться до wall deadline; старт до deadline не даёт неограниченного времени на выполнение. Гонку между submit и таймером определяем одним supervisor clock и тестируем управляемым fake clock.

**Награда при truncation:** согласно буквальному сочетанию пустого ответа и общей формулы, чистый эпизод может получить положительный return даже после timeout. Для ошибочного эпизода пустой ответ даёт F1=0. Не вводим произвольный override `-1` для всех truncation: такой override явно задан только для malformed submit. Всегда отдельно показываем `truncated` и причину завершения; этот нюанс вынесен в вопросы организаторам.

Oversized frame, бесконечный stdout, падение процесса и нарушение sandbox считаются ограниченными внешними сбоями агента: worker останавливается, эпизод truncates с пустым ответом, причина остаётся в trusted log. Транспортные лимиты и эта трактовка должны быть опубликованы.

## 5. Режимы train и closed

| Данные | Открытый train | Закрытый прогон |
|---|---|---|
| Исследовательская награда агенту | `0` | `0` |
| Терминальная награда агенту | Общая terminal reward | Всегда нейтральный wire `0` |
| Truth / provenance / scorer diagnostics | Не в наблюдениях; отдельные артефакты только для разрешённого анализа | Только evaluator до конца всего прогона |
| Публичные результаты инструмента | Только запрошенные записи / bounded error | То же |
| Объяснение правильности ответа в `info` | Не требуется; не выдаём | Запрещено |

Режим выбирает trusted harness, а не аргумент действия агента. Через reward, terminal observation и info нельзя понять правильность отправленных выводов в closed. Публичное подтверждение submit одинаково по содержанию для совпавших и несовпавших findings; валидация структуры может иметь отдельный evaluator-only reason.

После завершения всего закрытого прогона reviewer может открыть отчёт. Просмотрщик не связан обратным каналом с ещё работающим агентом и не читает live private логи во время закрытой проверки.

## 6. Детерминизм

Одинаковые `seed + normalized config + generator/schema/protocol version + actions` дают одинаковые public records, transitions и математические rewards. Нужны:

- собственные именованные RNG-потоки world / anomalies / presentation; стабильное derivation вместо `hash()`;
- фиксированные сортировки, ID canonicalization и однозначная нормализация JSON;
- деньги как целые minor units, FX/вычисления через Decimal, явная политика округления;
- timezone из manifest, зафиксированная tzdata; отсутствие зависимости от TZ/locale хоста;
- отсутствие wall-clock/`uuid4`/неупорядоченного set traversal в генерации и курсорах;
- новый immutable snapshot наблюдения на каждый шаг;
- отдельная каноническая часть replay и операционные метрики времени/RSS.

Реальные elapsed time, RSS, run timestamps и container ID не входят в каноническое сравнение replay и не возвращаются в agent `info`. Детерминированный программный timeout тестируется fake clock. Жёсткое wall-time ограничение на перегруженной машине не может обещать побитовую воспроизводимость моментов остановки: обеспечиваем существенный запас производительности, фиксируем железо и честно отделяем этот предел от детерминизма логики.

Для парных ID/order-тестов преобразуем все публичные ссылки, допустимые evidence sets и действия эквивалентной траектории согласованно. Оценка одного и того же по смыслу ответа при одинаковом inspection count должна сохраниться. Нельзя обещать одинаковое число шагов любого обычного агента после перестановки: его стратегия поиска может зависеть от порядка.

## 7. Калькулятор

Используем небольшой собственный parser для десятичных литералов, `+ - * /`, унарного знака и скобок. `eval`, `exec`, Python expressions целиком, функции, имена, атрибуты, индексация, строки, степени и файловые операции не поддерживаются.

Предлагаемые опубликованные пределы: expression <=512 символов, <=64 арифметических операций, глубина <=16, литерал <=40 значащих цифр; Decimal context precision 80; диапазон результата и длина ответа ограничены. Пределы можно скорректировать после измерений, не скрывая изменения в versioned config. Литерал переводится непосредственно из исходной строки в Decimal, без промежуточного float. Деление на ноль, неверный синтаксис и выход за диапазон дают bounded error и расходуют шаг.

Калькулятор не открывает файлы и не импортирует пользовательские модули. Сумма в итоговом findings всё равно сверяется независимо, а не доверяется тому, что агент вызвал calculator.

## 8. Поддерживаемая secure-изоляция

**Threat model:** агент может содержать произвольный непривилегированный Python-код и пытаться читать файлы, env, `/proc`, переданные FD, запускать процессы, писать в оценщик и открывать сеть. Доверяем supervisor, generator, evaluator, образу и ядру Linux. Эксплуатация уязвимостей ядра/контейнерного runtime и доказательство отсутствия всех ресурсных side channels не заявляются.

Один отдельный процесс под тем же UID с общим filesystem недостаточен. Проект secure profile:

1. Один Linux Docker container запускает доверенный supervisor. Private data живут вне дерева agent runtime и не передаются в него.
2. Минимальный readonly chroot агента создаётся при Docker build, а не собирается из private файлов во время эпизода. Внутри: Python runtime, public client/adapter и код выбранной политики. Нет generator/evaluator/private episode store, Docker socket, shell tools или host mounts. Нет `/proc` с процессами supervisor.
3. Запускаем **fresh exec** минимального launcher, а не fork-only Python worker из процесса с truth в памяти. Иначе агент может унаследовать private Python heap. Launcher стартует без пользовательских startup hooks (`-I -S -B` либо эквивалент), загружает только доверенный минимальный runtime и начинает выполнять policy только после sandbox setup. Для каждого эпизода/политики создаётся новый worker.
4. Launcher делает chroot и обязательно `chdir("/")`, очищает supplementary groups, устанавливает real/effective/saved UID/GID непривилегированного пользователя, сбрасывает capabilities, включает `no_new_privs`. Для setup нужны `SYS_CHROOT`, `SETUID`, `SETGID`; trusted parent дополнительно получает `KILL`, чтобы остановить worker после перехода на другой UID. Без `CAP_KILL` root с урезанными capabilities не гарантирует остановку такого worker. `SYS_ADMIN` не требуется. После смены UID effective/permitted/inheritable caps worker пусты; `no_new_privs` подтверждён probe. Agent root принадлежит root и недоступен для записи агенту; setuid/file capabilities не дают повысить права при `no_new_privs`.
5. В worker наследуются только stdin/stdout/stderr. Все private file descriptors, sockets, environment secrets и исходный cwd закрыты/заменены; нет seed в argv/env. Политика не получает writable filesystem в v1: кеширует открытые записи в памяти. Trusted tmpfs и output volume находятся вне chroot; таким образом scratch не переносит состояние между эпизодами и не требует опасной очистки attacker-created symlinks доверенным root-процессом.
6. Worker seccomp запрещает socket/network syscalls, ptrace/process-memory access и операции изменения namespaces/mounts. Выполнение policy начинается после установки ограничений. Три непривилегированные baseline-политики работают в этом профиле. Evaluator-only oracle остаётся отдельной доверенной ролью: отправляет обычный submit из evaluator harness, не передавая truth обычному worker и не выдавая привилегированный запуск за способность агента.
7. Container: `--network none`, readonly rootfs, ограниченные tmpfs, `--cpus 2`, `--memory 4g`, pids limit, `no-new-privileges`. Private output volume доступен supervisor и остаётся вне agent chroot. Worker получает дополнительные memory/CPU/FD/file-size лимиты.
8. Broker читает поток ограниченными порциями и лимитирует frame size/stdout/stderr. При deadline завершает всё дерево процессов policy. У агента нет канала отправить имя файла вместо tool ID.

Предварительная цель worker memory cap — 512 MiB; точное значение фиксируется после baseline измерений внутри общего лимита 4 GiB. Общий CPU/memory budget относится ко всему решению, а не по 2 CPU / 4 GiB каждому дочернему процессу.

**Первоначальный prerequisite gap:** на старте обнаружены macOS arm64, Python 3.12.1 и отсутствие Docker в PATH. В ходе M0 подготовлены Python 3.11.15 и отдельный Colima Linux ARM64 runner; глобальный default Docker context не менялся. Результаты раннего spike приведены ниже. Если требуемые primitive недоступны или leakage probes не проходят, secure verification прекращается с явной ошибкой. Нельзя тихо перейти к cooperative mode и показать зелёную проверку изоляции.

Если single-container spike не проходит, резервный проектный путь — два действительно изолированных контейнера с внешним trusted launcher: evaluator и агент, без Docker socket/секретов у агента, обмен только через ограниченный broker; либо согласованный Linux runner. Это отдельное deployment-решение, которое требует проверки доступности runtime и не считается уже реализованным. Rootless/bubblewrap возможен только при реально доступных user namespaces и проверенном профиле, а не как молчаливая замена.

### Обязательные security probes

- попытка открыть truth/provenance по известному абсолютному и относительному пути;
- обход ID через `../`, URL, null byte, неожиданные Unicode символы и ID другого эпизода;
- чтение trusted `/proc/*/environ`, `cmdline`, `fd` и памяти;
- чтение env/argv/FD worker на наличие seed/private config;
- запись в private store/evaluator/output volume;
- socket, DNS, HTTP и subprocess/shell escape;
- считывание закрытой correctness diagnostics из reward/info/error/log paths;
- stdout flood, oversized frame, зависание и дочерние процессы;
- повторный submit и reset-попытки для получения нескольких оценок.

Прохождение этих probes — проверяемая граница заявленной защиты, не доказательство абсолютной sandbox security.

## 9. Траектории и отчёт

Обязательные поля `trajectories.jsonl`: `episode_id, step, action, observation, reward, terminated, truncated`. Публичная траектория отражает именно то, что было доступно агенту: closed reward в ней `0`, закрытого truth в observation нет. Терминальная математическая награда closed хранится отдельно в private evaluator ledger и публикуется reviewer только после run. Открытая train-траектория может содержать terminal reward, но не truth в observation.

Private operational log дополнительно содержит версии, config digest без публикации seed агенту, причины исключений/завершений, ресурсы и TP/FP/FN/P/R/F1/return/steps/time. Private evaluator log и public trajectory нельзя склеивать в один файл, доступный agent runtime.

Отдельные роли артефактов:

- canonical replay fixture — сравнение детерминизма;
- public trajectory — воспроизведение опыта агента;
- private evaluation ledger — оценка и закрытые причины;
- post-run report — понятное reviewer объяснение, в том числе пары случаев и mutation-test результаты.

В README указываем, где в каждом режиме находятся эти файлы и кому они доступны.

## 10. Offline packaging и единая команда

Поддерживаемый путь проверки не зависит от загрузки base image, pip/apt, API или моделей во время official run. Предлагаемый release:

- исходники с лицензией, lockfile и hashes;
- заранее собранный OCI/Docker image tar для согласованной Linux architecture;
- версия схем/config, публичные 10 train + 10 dev эпизодов и проверки;
- shell-wrapper, который локально делает `docker load`, затем запускает pinned image с `--pull=never` и `--network none`;
- README с одной командой `./scripts/verify --offline` и отдельными командами разработки/демо.

Подготовка образа может использовать сеть заранее; автономный runtime — нет. Не выдаём обычный `docker build`, которому нужны интернет и незакешированный base image, за offline проверку. Wheelhouse/offline build может быть дополнительным путём, но не заменяет проверенный release artifact.

Проверяем размер всего передаваемого решения; ориентир <1 GB. В отчёте отдельно размер tar и распакованного образа, чтобы неоднозначность лимита не скрывалась. Пока operational assumption — Linux/amd64; её требуется подтвердить. На Apple Silicon эмуляция amd64 не равна официальному железу по скорости; архитектура и факт эмуляции обязательно записываются в отчёт.

При отсутствии Docker/поддерживаемого sandbox wrapper даёт ясную ошибку. `python -m ... --cooperative` допустим для разработки, но не является успешной secure verification.

## 11. Реализация по этапам и критерии готовности

| Этап | Результат | Gate перед следующим этапом |
|---|---|---|
| E0. Protocol + security spike | Политика обменивается JSONL из chroot с отдельным UID | Baseline работает; private path/env/FD/proc/network probes не проходят у агента; fail-closed проверен |
| E1. Lifecycle + tools | reset/step, полный набор инструментов, стабильные курсоры, калькулятор | Тесты шагов 99/100/101, invalid input, submit/timeout/reset; никакого eval |
| E2. Store + determinism | Seeded public store, полные записи, канонический replay | Одинаковые actions повторяются; максимальный supported episode читается <=50 inspection |
| E3. Train/closed + scorer | Разделение wire и private evaluation | Closed правильный/неправильный submit не раскрывает score; repeated submit не пересчитывает оценку |
| E4. Adapters + resources | Все четыре baseline adapters работают offline | <=100 steps, без сети/GPU/API; wall/RSS/CPU измерены на максимальных config |
| E5. Release + report | Image tar, single command, trajectory/report outputs | Проверка на чистом Docker с отсутствующим image cache и отключённой сетью; size/versions зафиксированы |

Для E0 не нужна готовая бухгалтерия: достаточно одного синтетического открытого документа и private sentinel. Для E1 используем небольшой record fixture. Это позволяет обнаружить риск sandbox до инвестиций в полный генератор.

## 12. Вопросы организаторам и консервативные defaults

1. Полный перечень фиксированных contract/scorer/paired проверок и точный adapter wire. Пока публикуем свой versioned JSON протокол и явные адаптеры.
2. `inspection_steps`: считать ли неверные non-submit действия? Default: да. Считать ли submit? Default: нет, но он входит в total100.
3. Разрешён ли submit100 и что возвращать после завершения? Default: submit100 разрешён, последующие вызовы отклоняются без новой награды.
4. Какая scalar wire reward ожидается в closed? Default: `0` везде; истинная награда только private evaluator.
5. Применяется ли общая формула к пустому ответу при timeout на чистом эпизоде или нужен отдельный override? Default: буквально общая формула; status всегда отдельно.
6. Что именно входит в 60 секунд и 1 GB? Default: консервативный end-to-end episode wall budget и учёт всех release artifacts.
7. Поддерживаемые Linux architecture, Docker capabilities и способ запуска организаторских политик. Без подтверждения sandbox профиль остаётся ранним проверяемым operational assumption.
8. Точный полный способ чтения policy/FX и допустимость public ID tool-envelope. Default: `get_document("policy")`, fx IDs в envelope, обязательные CSV поля сохранены.
9. Считается ли наличие полноценного proof-set достаточным независимо от того, открывал ли агент эти ID? Не добавляем неподтверждённое требование «обязательно прочитать ранее».

## 13. Основные риски

- **Security profile не поддерживается:** рано проверяем E0; не скрываем cooperative fallback.
- **Правильность и правда утекли через отчёт:** разделяем writer/volume и откладываем closed reviewer report до конца run.
- **Бюджет сделал эпизод недоступным:** полные записи в list_records + preflight bound.
- **Скрытая недетерминированность:** фиксируем locale/timezone/tzdata/RNG/JSON, отделяем operational metadata.
- **Offline package зависит от сети:** проверка load+run на чистом кеше с network none.
- **Тайм-ауты недетерминированы на границе:** запас по производительности, fake-clock contract tests, отдельная диагностика.
- **Слишком сложная архитектура:** один trusted supervisor, один worker, pipes, один secure Linux profile; viewer читает готовые артефакты, а не вмешивается в environment.

## 14. Фактический Stage 1 и ранний G0, 19 ноября

Реализованы `src/fin_audit/environment.py` и `calculator.py`; интерфейсы интегрированы с генератором и оценщиком. Локально прошли 90 проверок среды/калькулятора, включая реальный generate -> reset -> two inspections -> oracle submit с двумя issues, reward 0.996, точный replay и новый seed. Это tests-only oracle, не утверждение о способности обычного агента.

В `AuditEnv` есть trusted-only `abort(reason)` для остановки worker и `remaining_time_seconds` для единого бюджета broker. Они не являются доступными агенту инструментами. При abort итог пустой; общий reward считается обычной формулой. После завершения повторные step/abort не меняют результат и не возвращают terminal reward повторно.

Собран `genesis-fin-audit:stage1` в отдельном Docker context `colima-genesis-fin-audit`. В проверенном раннем образе: Python 3.11.15, Linux ARM64, `libseccomp2` 2.5.4-1+deb12u1; jail занимает около 41.3 MB и не содержит trusted application/site-packages. Python base image закреплён реально полученным manifest digest в Dockerfile; test dependencies установлены из `uv.lock` с проверкой SHA-256.

Реальный запуск пяти security tests завершился `5 passed`, без skips, при `--network none --read-only --cap-drop ALL --cap-add SYS_CHROOT --cap-add SETUID --cap-add SETGID --cap-add KILL --security-opt no-new-privileges --pids-limit 64 --cpus 2 --memory 4g --tmpfs /tmp:rw,nosuid,nodev,size=128m`. Проверены actual worker probes, очистка переданного private FD/seed env, остановка worker после UID drop, fail-closed nonroot launcher и readonly состав jail. В образе `FIN_AUDIT_REQUIRE_SECURE=1` превращает отсутствие prerequisites в test failure; локальные non-Linux skips не считаются этой проверкой.

Два реальных дефекта подготовки были обнаружены и исправлены до зелёного G0: slim runtime содержал опциональный `_tkinter` extension без Tk-библиотек (исключён из jail), а chroot fresh exec требовал публичный `/etc/ld.so.cache` для обнаружения libpython без `/proc`. Дополнительно `.dockerignore` исключает nested pycache, чтобы в образ не попадали локальные bytecode paths.

Пределы подтверждения: это ранний kernel/runtime spike на ARM64 и Stage 1 native-currency среда. Не заявлены готовность FX/cutoff/всех interactions, официальные hidden checks, Linux/amd64 производительность, абсолютная sandbox security или финальный offline release rehearsal. Финальная версия образа должна пересобираться после интеграционных изменений и проверяться целиком.
