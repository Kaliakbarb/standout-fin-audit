## 2. Обязательный контракт оценивания

`submit` принимает объект с `episode_id` и массивом `findings`. Каждая находка содержит `type`, `affected_ids`, `claimed_amount_minor`, `currency`, `evidence_ids`, `explanation`.

Обязательные пределы из кейса:

- не больше 30 находок;
- не больше 10 ID доказательств на находку;
- не больше 1000 символов объяснения на находку;
- неверная структура завершает эпизод с наградой -1;
- выводы сопоставляются с эталоном взаимно однозначно;
- TP требует правильных типа, канонических affected IDs, суммы в объявленном допуске, валюты и полного допустимого набора доказательств;
- несопоставленные и повторные находки дают FP, ненайденные ошибки дают FN;
- короткое объяснение предназначено для читателя; убедительность текста не влияет на награду.

### 2.1. Публичные проектные решения

Перечисленные далее трактовки фиксируем в версии схемы и документации до создания train/dev. Они уточняют недоопределённые места кейса, а не приписываются организаторам.

1. `claimed_amount_minor` и `expected_amount_minor` — неотрицательный модуль расхождения в базовой валюте компании. Знак и направление расхождения указаны в коротком расчёте. Конкретные канонические affected IDs и формулы каждого семейства согласуются с `data-design.md`.
2. Деньги проверяются как JSON integers с явным отклонением boolean. Внутренние финансовые вычисления используют integer minor units и Decimal; float не участвует в определении суммы ошибки.
3. Допуск — опубликованное абсолютное целое число minor units по типу. Предпочтительный default — 0, поскольку генератор и checker считают по одним объявленным правилам округления без измерительного шума. Если нужен допуск 1, причина и значение публичны. Оценщик не подбирает допуск к ответу агента.
4. ID — непрозрачные публичные строки. Не приводим их к lower-case, не удаляем префиксы и не угадываем связи. `affected_ids` канонизируются как точное множество; повтор ID внутри одного массива не создаёт новый объект. Повтор всей находки остаётся отдельным предсказанием и потенциальным FP.
5. Типы и валюты имеют опубликованные канонические имена. Неизвестная строка типа или неверная строка валюты — семантическая ошибка находки, которая не создаёт ребро совпадения. Это не повод произвольно спасать ошибочный ответ через alias или fuzzy matching.
6. Поля схемы, обработка неизвестных ключей, namespace ID и версия нормализации фиксируются явно. При предпочтительном строгом JSON Schema дополнительные поля запрещены; это проектная политика, которую сверяем с официальными примерами до заморозки.
7. Отсутствие обязательного поля, неправильный JSON-тип, нарушение пределов и нечисловые значения внутри распознанного submit — структурно невалидный submit. Неизвестный ID, существующий ID от другого эпизода, неправильная сумма и неполные доказательства — семантический отказ в совпадении. Полностью неразбираемый JSON frame, oversized transport и stdout flood обрабатывает broker по отдельному опубликованному протоколу среды; matcher не пытается угадать по строке, был ли это submit.
8. Пустой массив находок валиден. Пустой массив affected/evidence IDs у находки не совпадает ни с одной реальной ошибкой; не превращаем его молча в догаданную ссылку.
9. `episode_id` должен совпасть с текущим эпизодом. Предпочтительная трактовка несовпадающего envelope — invalid submit с -1; официальный пример требуется запросить.

### 2.2. Публичный registry доказательств

Каждый допустимый ID должен разрешаться разрешённым инструментом в открытые записи текущего эпизода. Registry не содержит issue ID, типа мутации, seed, правильного ответа или отметки «доказательство ошибки».

Ledger использует публичный `row_id`, документы используют `doc_id`. Для FX и policy, у которых минимальная схема не задаёт ID, обязательные файлы не меняем ради адресации: FX ID находится в публичном tool envelope/index, policy имеет зарезервированный публичный ID `policy` и доступна через `get_document('policy')`. Точные wire envelope и правила registry задаёт `environment-design.md`. Дополнительные accounting metadata и расширения схем рассматриваются отдельно и не нужны только для FX-адресации.

Доказательство задаётся как один или несколько альтернативных полных наборов ID. Для находки с набором `E` существует допустимое доказательство, если хотя бы один полный набор `S` удовлетворяет `S ⊆ E`. Наш provisional default: все присланные ID должны существовать и принадлежать текущему открытому эпизоду. Лишние существующие доказательства допустимы в пределах 10 ID; они не дают бонуса. Отказ за лишний неизвестный ID, когда полный корректный набор уже присутствует, не определён в кейсе явно; это открытая трактовка до официальных примеров, а не официальное правило.

Полнота — содержательное свойство документов, а не только совпадение ID. При `invoice_refs=null` нельзя объявить allocation-ошибку без другого открытого однозначного документа назначения. Policy задаёт правило обработки, но не изобретает отсутствующий хозяйственный факт. Каждый альтернативный proof-set обязан самостоятельно доказывать назначение; набор, который обходит необходимый неизвестный факт, недопустим.

Не вводим дополнительное правило «документ обязательно должен был быть ранее запрошен агентом»: такого обязательства в предоставленном кейсе нет. Угаданный существующий ID сам по себе не делает правильное полное доказательство неверным. Атака угадыванием проверяется через существование, принадлежность, достаточность и сопоставление доказательств, а не через недокументированную санкцию.

### 2.3. Согласованные канонические правила v1

Таблица согласована с направлением данных. Это публичная семантика нашего решения, а не недоступная агенту договорённость между генератором и оценщиком.

| Type v1 | Точное множество affected IDs | Expected amount в base currency |
|---|---|---|
| `duplicate_invoice` | Все primary AR-debit recognition row IDs одного invoice, включая оригинал и лишние записи | Избыточная gross recognition сумма при фактически применённой оценке |
| `payment_allocation` | `payment_id` и `invoice_id` | Избыточный UNALLOCATED credit при фактически наблюдаемой оценке платежа |
| `fx_conversion` | Primary ledger row ID: AR-debit для recognition, cash-debit для payment | Модуль разницы observed primary amount и правильной конвертации source amount |
| `period_cutoff` | Primary affected ledger row ID: AR-debit или cash-debit | Наблюдаемая сумма primary row, чей целый balanced journal переносится в правильный период |

Для дублей группа считается одним issue, а не числом пар дублирующих строк. Полные evidence sets могут включать другие стороны journal, документ, FX row и policy, даже если affected set состоит только из primary ID.

Каждый тип имеет публичный условный repair operator: исправляется конкретное нарушение при остальных наблюдаемых величинах. Поэтому суммы разных типов не суммируются как общий ущерб и могут изменяться после исправления другой ошибки. Правило обязательно объясняется на комбинированном примере; peer-проверка этого правила важнее краткости названия amount.

## 3. Matcher без зависимости от порядка ответа

### 3.1. Вход и границы доверия

Matcher получает только валидированный submit, закрытый `TruthIssue[]`, публичную версию политики нормализации/допусков и registry открытых ID. Сам matcher не принимает от агента число шагов, reward, TP или FN.

При запуске генератора отдельный валидатор уже подтвердил, что truth соответствует открытым данным. Наличие записи в provenance не является доказательством для matcher или checker.

### 3.2. Условия потенциального совпадения

Между предсказанием `f` и эталонной ошибкой `t` создаётся ребро только при одновременном выполнении:

1. тип совпадает с публичным каноническим типом;
2. канонические множества affected IDs точно равны;
3. валюта совпадает, без неявной конвертации на этапе matching;
4. `abs(f.amount_minor - t.expected_amount_minor) <= public_tolerance_minor(type)`;
5. каждый evidence ID валиден и хотя бы один полный допустимый набор доказательств содержится в ответе;
6. находка и ошибка принадлежат одному текущему эпизоду.

Похожие суммы, общий контрагент, красивое объяснение, пересечение части evidence или вхождение истинных affected IDs в огромный набор не считаются совпадением.

### 3.3. Взаимно однозначное сопоставление

Строим двудольный граф «предсказания — эталон». Ищем matching максимальной мощности детерминированным алгоритмом увеличивающих путей. Зависимость от сторонних scientific-пакетов не нужна: до 30 предсказаний и рекомендуемые 0–12 ошибок делают задачу маленькой.

В общем случае простой greedy по первому подходящему эталону недостаточен: если `f0` подходит `t0,t1`, а `f1` только `t0`, он может получить 1 TP вместо 2. Отдельный matcher-only fixture ловит этот случай как защиту общего алгоритма. В нашем generated truth действует uniqueness `(type, canonical affected IDs)` и точное сравнение этих полей, поэтому такая неоднозначность не должна возникать в корректном реальном эпизоде. Этот synthetic fixture не выдаём за доказательство сложности или наличие неоднозначных бухгалтерских ошибок.

Порядок обхода задаётся явно и стабильно. При нескольких максимальных matching число TP/FP/FN и reward одинаковы; выбор конкретных пар для приватного диагностического отчёта имеет опубликованное детерминированное разрешение. Перестановка находок или truth не должна менять метрики.

Финальные счётчики:

- `TP = число пар в maximum matching`;
- `FP = число всех присланных находок - TP`;
- `FN = число truth issues - TP`.

Находки не дедуплицируются перед подсчётом FP. Одна эталонная ошибка не может поглотить несколько одинаковых ответов.

## 4. Метрики и общая награда

Для валидного итогового массива:

- `P = TP/(TP+FP)`, при нулевом знаменателе 0;
- `R = TP/(TP+FN)`, при нулевом знаменателе 0;
- `F1 = 2TP/(2TP+FP+FN)`;
- если truth и findings пусты, `F1 = 1` при `P = R = 0`;
- если truth пуст, но findings непуст, `F1 = 0`;
- `common_return = clip(2*F1 - 1 - 0.002*inspection_steps, -1, 1)`.

F1 не округляется перед вычислением награды. Предпочтительно считать отношения и coefficient как рациональные числа либо Decimal, затем сериализовать reward конечным JSON-числом. Денежные суммы никогда не переходят в float.

Return равен единственной терминальной награде; исследовательские шаги имеют reward 0. Экспериментальная reward не нужна для первой версии. Если она появится, общий результат остаётся отдельной обязательной колонкой.

### 4.1. Согласованный счёт шагов

Проектная трактовка, согласованная со средой:

- общий бюджет максимум 100 попыток действий включает submit;
- `inspection_steps` включает все принятые не-submit попытки, в том числе неправильный action, неизвестный ID и ошибку калькулятора;
- submit расходует общий шаг, но не является inspection;
- валидный submit как 100-е действие после 99 inspections разрешён;
- 100-е не-submit действие приводит к truncation, итоговый массив пуст;
- после завершения итог и награда неизменяемы, повторный submit не даёт новую попытку;
- counters передаёт доверенная среда, агент их не задаёт.

Должна быть однозначная линейная точка фиксации submit при гонке с wall-clock timeout. Это решение реализует среда и показывает в тестах.

### 4.2. Особые завершения

Неверная структура submit имеет явный override награды -1. Для отчёта рекомендуем `status=invalid_submit`, `P/R/F1=null`, reward=-1: метрики не выдумываются для несуществующего валидного ответа. Если официальный harness требует числовые P/R/F1, формально согласуем отдельную конвенцию, сохраняя -1.

Для timeout/step-limit кейс задаёт `truncated=true` и пустой итоговый ответ, но отдельный override -1 не указан. Поэтому до официального уточнения применяем общую формулу к пустому результату:

- на ошибочном эпизоде F1=0 и reward=-1;
- на чистом эпизоде F1=1 и reward может быть положительным: при 100 inspections это 0.8.

Не заменяем общую функцию незаявленным штрафом -1 для всех тайм-аутов. Отдельно показываем долю truncation, иначе средняя награда скрывает незавершённые чистые случаи.

## 5. Independent checker: корректность и полнота truth

Нужны два разных утверждения:

1. Каждая объявленная ошибка действительно следует из открытых записей и политики.
2. В поддерживаемой модели нет дополнительных незаписанных ошибок; чистый эпизод действительно чист.

Checker, который только подтверждает перечисленные truth issues, не доказывает второе. Поэтому проверяющий должен независимо пересчитать поддерживаемые связи invoice/payment/ledger/FX/period по всему эпизоду и сравнить восстановленный набор расхождений с truth.

Поддерживаемая бухгалтерская модель должна быть намеренно ограниченной и публично описанной. Повторение полного универсального бухгалтерского движка не требуется. Повторное использование чистых примитивов parsing/minor-unit arithmetic допустимо; использование формулы мутации или её закодированного expected answer как проверки самой себя недопустимо.

Для каждого issue checker проверяет доступность полного witness, корректность суммы, связей и политики. Для каждого clean distractor — отсутствие нарушения. Для комбинированных мутаций — отсутствие случайных дополнительных расхождений и нулевых эффектов, помеченных ошибками.

На allocation+FX необходимо условное определение эффектов: allocation оценивает избыточный UNALLOCATED credit при наблюдаемой оценке платежа, FX — разницу полной primary cash-суммы и правильной конвертации source payment. Эти проектные семантики должны быть полностью публичны. Нельзя независимо посчитать два эффекта на исходной полной сумме и просто сложить их: возможен двойной счёт взаимодействия.

Проверенный при проектировании пример из направления данных: invoice $1000 при carrying rate 500; payment $600 с правильным rate 505, ошибочно оценён по 495; распределено $500. Balanced journal: debit cash 297000 + FX loss 2500 = credit AR 250000 + UNALLOCATED 49500. В наблюдаемом состоянии allocation issue=49500, FX issue=6000. После исправления FX amount allocation становится 50500. Это демонстрирует реальную зависимость величин. Числа служат hand-checked fixture, не результатом ещё не выполненного запуска программы.

## 6. Четыре адаптера базовых политик

Официальный список политик известен, точный код организаторов не предоставлен. Реализуем reference policies и тонкий интерфейс подключения официальной политики. Не утверждаем, что локальная эвристика идентична неизвестному коду организаторов.

### 6.1. Random explorer

Собственный фиксированный policy seed, не равный скрытому seed генератора по умолчанию и не получаемый из приватного manifest. Политика видит только обычные observations и tools. Случайность воспроизводится. Она обязана оставить шаг на submit или честно завершиться truncation; случайный baseline не следует специально делать заведомо структурно невалидным.

### 6.2. Simple reconciliation

Детерминированная простая сверка на публичных полях: получать записи страницами, связывать доступные invoice/payment IDs, применять опубликованную policy, формировать краткие доказательства. Никаких прямых файлов, private truth/provenance, импорта generator internals или альтернативного SQL-интерфейса. Полный independent checker также не импортируется как simple baseline: это отдельный доверенный verifier, отсутствующий в agent runtime. Общие parsing/arithmetic примитивы использовать можно.

Её качество — диагностическая величина. Высокий результат сам по себе не плох и не требует намеренно запутывать данные. Сложность добавляется законными distractors и взаимодействиями, сохраняя разрешимость.

### 6.3. Mark-all attack

Нужны два локальных негативных сценария: валидный shotgun в пределах 30 находок и структурно переполненный submit. Если вся атака состоит только в превышении лимита, мы не проверим устойчивость matcher к валидным ложным обвинениям.

Для валидного shotgun используем публичные строки и известные типы; не читаем truth при выборе. Дополнительно точечные атаки проверяют affected supersets, повтор верного ответа, смешение валют и неполные evidence.

### 6.4. Evaluator-only oracle

Oracle привилегированно получает верные находки и полные evidence от доверенного evaluator и отправляет их через обычный submit. Он не является обычной политикой агента и никогда не инъецирует truth в observation. При 0 inspections его общая награда может быть 1; это проверка верхней границы оценщика.

Oracle не доказывает, что ошибку способен обнаружить агент по наблюдениям. Обнаружимость и достаточность доказательств проверяются отдельно. Закрытые oracle-логи остаются у оценщика до завершения закрытого прогона и не доступны последующим агентам.

## 7. Локальный протокол оценки

### 7.1. Публичные и закрытые наборы

Обязательные артефакты сдачи — 10 открытых train и 10 dev эпизодов. Отдельно создаём локальный контрольный batch из 20 иных эпизодов: 5 чистых, 5 с взаимодействиями, остальные покрывают отдельные типы и параметры. Это локальная репетиция структуры закрытого прогона, а не попытка предсказать скрытые seed.

Все четыре политики выполняются на одних и тех же 20 мирах. Для каждой политики окружение сбрасывается и её состояние изолируется; не допускаем общей памяти о ранее открытых приватных данных.

Дополнительно выполняются 20 парных проверок с перестановкой строк и согласованной заменой всех ID/ссылок. Контрольный oracle или эквивалентно преобразованные findings с одинаковым inspection budget сохраняют TP/FP/FN/F1/reward. У обычной политики порядок чтения и число шагов могут измениться: её производительность измеряется отдельно, не обещаем всем агентам одинаковую траекторию после shuffle.

Held-out параметры включают и новые сочетания известных типов/валют/размеров/периодов, а не только новые seed. Новые обязательные семейства ошибок тайно не добавляются.

### 7.2. Измеряемые поля

Для каждого эпизода сохраняем status, TP/FP/FN, P/R/F1, common return, число общих и inspection шагов, время, agent policy/version, config/schema version и доверенный replay reference. Private seed/truth доступны только в evaluator-артефакте.

Показываем отдельно:

- значения каждого эпизода;
- macro mean F1/return и распределение шагов/времени;
- clean false-accusation rate;
- долю валидных submit и truncation;
- результаты по типам и взаимодействиям;
- дополнительные micro metrics по суммарным counts, явно отделённые от официальной per-episode формулы.

Не вычисляем общий F1 из усреднённых P/R. Чистый эпизод с P=R=0 и F1=1 соответствует объявленной конвенции. Значения oracle не выдаются за способность агента.

### 7.3. Детерминизм и производительность

Сначала проверяем точное воспроизведение семантических записей, actions/observations, flags и наград. Wall-clock duration, PID и временный путь не входят в сравнение детерминированного transcript. Если они нужны evaluator-журналу, держим их в отдельной недетерминированной метаинформации.

Рекомендуемые ограничения кейса превращаем в явную целевую конфигурацию: Python 3.11, 2 CPU, 4 GB RAM, без GPU/сети, 60 секунд на эпизод, до 1 GB solution. Проверяем cold start и размер образа/артефактов отдельно, уточнив у организаторов, входит ли container image в 1 GB.

## 8. Матрица требований и проверяемых свидетельств

Это рабочие группы локальных тестов. Полные официальные 20 проверок в каждой категории ещё не предоставлены.

| Критерий | Что локально проверяем | Свидетельство для сдачи |
|---|---|---|
| Контракт/изоляция, 25 | reset isolation, step schema, error cost, stable pages, boundary100, submit/timeout, no seed/truth leaks, no private write, calculator sandbox | machine-readable conformance report и sanitized trajectories |
| Данные/эталон, 25 | корректный clean world; четыре независимых типа; два реально зависимых interactions; positive effects; достаточные proof sets; отсутствие незаявленных ошибок | independent checker report для каждого эпизода |
| Награда, 25 | positive/negative fixtures; duplicates; full evidence; currency/tolerance; one-to-one matching; shotgun; malformed; no hidden interim feedback | matcher/reward test report, открытые normalization/tolerance rules |
| Воспроизводимость/обобщение, 15 | same-seed/action replay; ID/order transforms; novel declared combinations; no seed-derived public labels | pairwise/replay report с объяснёнными сравниваемыми полями |
| Инженерия/объяснение, 10 | одна команда; config versions; траектории; измеренный failure analysis; honest limits | README, CLI report, design note, воспроизводимые примеры сбоев |

Каждый тест ссылается на requirement ID общего `docs/REQUIREMENTS.md`. Нельзя объявлять «прошли 20/20 официальных» на основании самостоятельно названных групп.

## 9. Тестовый набор оценщика

Минимально необходимые классы:

1. Валидный полный ответ по каждому типу и двум interactions.
2. Валидное молчание на чистом и ошибочном эпизодах.
3. TP с полным evidence против того же claim с одним обязательным ID меньше.
4. Существующие лишние evidence против несуществующих и cross-episode ID.
5. Неправильная валюта при совпавшем численном amount.
6. Точный amount, граница tolerance и значение сразу за ней.
7. Неправильный type, missing affected ID и affected superset.
8. Дубли находок до и после правильного ответа; порядок не влияет на counts.
9. Generic matcher-only greedy trap: maximum matching находит больше TP; отдельно generator не допускает неразличимых truth keys.
10. В распознанном submit: JSON boolean вместо integer, null вместо массива, missing field, over30/over10/over1000. Неразбираемый JSON frame и oversized/flood transport проверяются отдельно на уровне среды.
11. Safe valid submit на 100-м шаге, truncation на 100-м inspection, timeout до submit и неизменность завершённого состояния.
12. Guessed IDs без полного proof, повторная отправка, «пометить всё», attempted reward/counter injection.
13. Поля explanation не влияют на reward при одинаковых семантических полях.
14. Трансформации ID/порядка не меняют matching для эквивалентных выводов.
15. Нулевой эффект мутации после округления не появляется как обязательная ненулевая ошибка.
16. `invoice_refs=null` без другого открытого назначения не создаёт allocation truth; альтернативные proof sets не подменяют отсутствующий факт догадкой.

Нужны как hand-checked fixtures с малым числом записей, так и property-based проверки на независимо выбранных конфигурациях. Число успешных random-примеров не заменяет покрытие классов и не доказывает отсутствие ошибок.

## 10. Дифференциатор: проверяем и аудитора, и экзаменатора

Эти возможности усиливают достоверность решения и объяснение, но не получают отдельного бонуса за оригинальность.

### 10.1. Парные причинные случаи

Для изолированной ошибки создаём корректный и изменённый вариант одного мира. При устранении причины соответствующее обвинение перестаёт быть правильным, остальные ожидаемые связи контролируются. Для взаимодействующих ошибок пересчитываем все зависимые эффекты; нельзя без проверки обещать «исчезнет ровно один issue».

Добавляем пары похожих наблюдаемых признаков: законные повторяющиеся суммы против дубля одной операции, легальная частичная оплата против потери распределения. Никаких доступных agent-флагов clean/dirty.

### 10.2. Mutation-тесты оценщика

В test-only harness создаём известные дефектные варианты matcher/reward:

- игнорируется currency;
- вместо полного proof требуется любое пересечение evidence;
- один truth допускает несколько TP;
- affected IDs сравниваются по subset;
- исчезает FP или FN из F1;
- clean-empty F1 ошибочно становится 0;
- tolerance проверяется с неправильной границей;
- greedy заменяет maximum matching;
- шаги не вычитаются из общей награды.

Сначала правильный evaluator проходит набор; затем каждый дефект должен вызывать предсказуемый тестовый отказ. Отчёт содержит фактически внесённые defects, тесты, которые их обнаружили, и surviving mutants. При наличии survivor не скрываем его, а устраняем пробел в тестах или объясняем эквивалентность.

В production runtime нет доступного агенту переключателя «ослабить оценщик». Демо поломки работает в отдельном test-only процессе. Mutation score — инженерная диагностика, не официальный балл и не доказательство полной корректности.

### 10.3. Показательный сценарий с маскировкой

В вымышленной политике invoice A=50 000 KZT проведён дважды; invoice B=1000 USD вместо положенного курса 500 пересчитан по 450. Ожидаемая сумма 550 000 KZT и фактическая 550 000 KZT совпали, отдельные эффекты +50 000/-50 000 скрылись в агрегате. Ledger может оставаться double-entry balanced.

Этот пример показывает недостаточность одних агрегатов и требует отдельных доказательств двух ошибок. Это маскировка, а не замена обязательных двух сценариев с реальной зависимостью расчётов. Валидатор проверяет и этот эпизод целиком.

### 10.4. Компактный post-run viewer

Viewer читает завершённые настоящие журналы и evaluator reports. Показывает наблюдения, действия, документы, краткие расчёты, verdict и изменения в парных случаях. Не выдумывает chain-of-thought, не подменяет записи заранее подготовленной картинкой, не требует сети.

Во время closed run truth, reward, диагностика и сертификаты недоступны агенту. Раскрытие отчёта — только после завершения всего закрытого прогона. UI создаём последним и держим вне критического пути официального CLI.

## 11. Roadmap с критериями готовности

### E0 — заморозка публичной семантики

Выход: версия schema/policy; type-specific amount/affected/evidence rules; явно перечисленные неясности. Готово, когда все три направления согласовали канонические связи, денежные формулы и termination/counter rules. При официальном уточнении версия меняется, fixtures обновляются до генерации финальных наборов.

### E1 — минимальный полный путь

Выход: один чистый и один ошибочный эпизод, tools-only agent, submit, matcher, common reward, sanitized transcript. Готово, когда hand-checked суммы/TP/FP/FN/reward совпадают, воспроизведение точное, malformed submit и clean ложное обвинение дают ожидаемое поведение.

### E2 — полный обязательный набор

Выход: четыре типа, два взаимодействия, distractors, четыре reference adapters, 10 train/10 dev. Готово, когда independent checker подтверждает корректность и полноту каждого эпизода, а все baseline проходят через одну среду/оценщик.

### E3 — системная устойчивость

Выход: атакующие submit fixtures, boundary tests, stateful action tests, ID/order transformations, held-out combinations, измерения ресурсов и security probes. Готово, когда каждый requirement имеет тест/артефакт и нет известного необъяснённого нарушения общего контракта.

### E4 — усиление доказательств

Выход: mutation report, парные причинные случаи, сценарий маскировки. Готово, когда intentional faults пойманы реальными тестами, effects пересчитаны независимо и нет fabricated результатов.

### E5 — сдача и объяснение

Выход: автономная одна команда проверки, отчёты, trajectories.jsonl, locked dependencies, лицензия, design note, README, короткое демонстрационное прохождение. Viewer добавляется только при зелёном ядре. Готово после clean offline run из свежего контейнера на целевых ресурсах и проверки всех артефактов по checklist.

## 12. Вопросы организаторам, не блокирующие первый прототип

1. Где полный опубликованный набор определений фиксированных проверок и официальные schema/examples?
2. Как определяются expected amount/currency и canonical affected IDs для четырёх типов, особенно при взаимодействии?
3. Что именно считается inspection step, допускается ли submit100 и как разрешается гонка submit/time limit?
4. При truncation на clean применять common formula к empty final или есть специальная награда?
5. Требуется ли доказательство ранее прочитать? Как оценивать unknown extra evidence, envelope episode mismatch и неизвестные ключи?
6. Как wire-контракт скрывает reward в closed mode, какие поля допускает info, когда заканчивается весь закрытый run?
7. Какой threat model агента и deployment topology проверяются? Что входит в 1 GB решения?
8. Как подключаются точные политики организаторов, и какой expected CLI/protocol у checker?

До ответов используем явно опубликованные проектные решения, не маскируем их под официальный стандарт. Не вводим дополнительные обязательные типы ошибок и не изменяем общую reward ради красивой демонстрации.
